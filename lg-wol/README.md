# بیدارباش شبکه برای تلویزیون‌های ال‌جی (webOS)

یک اپ **Wake On LAN** برای تلویزیون‌های ال‌جی با سیستم‌عامل webOS. کامپیوتر، NAS،
کنسول یا پخش‌کنندهٔ رسانهٔ خواب‌رفته را روی شبکهٔ خانه از روی تلویزیون روشن می‌کند.

---

## ⚠️ یک نکتهٔ مهم که باید قبل از هر چیز بدانید

**تلویزیون نمی‌تواند خودش را بیدار کند.**

این محدودیت فنی است، نه ضعف این اپ: تلویزیونِ خاموش هیچ کدی اجرا نمی‌کند، و هر اپ
webOS هم فقط *روی* تلویزیون اجرا می‌شود. پس این اپ برای روشن کردن **دستگاه‌های
دیگر** روی همان شبکه است — کامپیوتر، NAS، رزبری‌پای، کنسول.

اگر هدفتان روشن کردن خود تلویزیون از راه دور است، به اپ روی تلویزیون نیازی ندارید؛
خود ال‌جی این کار را با قابلیت **LG ThinQ** یا روشن شدن با HDMI-CEC انجام می‌دهد.

## ساخت و نصب

```bash
cd lg-wol

npm run icons      # ساخت icon.png و largeIcon.png (الزامی، اپ webOS بدون آیکون بسته‌بندی نمی‌شود)
npm test           # آزمون منطق بستهٔ جادویی و تجزیهٔ ARP روی همین کامپیوتر
npm run package    # خروجی: dist/com.zcode.wol_1.0.0_all.ipk
```

نصب روی تلویزیون:

```bash
npm run device:add      # افزودن تلویزیون؛ در حالت تعاملی نام و IP را وارد کنید
npm run install:tv      # نصب بستهٔ .ipk
npm run launch          # اجرا
npm run log             # دیدن لاگ سرویس، برای عیب‌یابی
```

**نصب روی تلویزیون خودت، بدون فروشگاه ال‌جی، کاملاً ممکن است** — با حالت
توسعه‌دهنده و همین `ares-cli`. حساب فروشنده (که مدارک شرکت می‌خواهد) لازم نمی‌شود.
راهنمای گام‌به‌گام با همهٔ دستورها، عیب‌یابی نصب، و محدودیت تازه‌سازی دوره‌ای نشست
توسعه‌دهنده در **[INSTALL.md](INSTALL.md)** آمده است.

## معماری

مرورگر داخل webOS در یک سندباکس اجرا می‌شود و اجازهٔ باز کردن سوکت UDP خام را
ندارد. بنابراین ارسال واقعی بسته در یک **سرویس Node.js** انجام می‌شود که داخل خود
اپ قرار دارد:

```
index.html + js/*.js        رابط کاربری (مرورگر سندباکس‌شده)
        │
        │  luna://com.zcode.wol.service/send   ← از طریق PalmServiceBridge
        ▼
service/service.js          سرویس Node.js  ← اینجا سوکت UDP باز می‌شود
        │
        │  بستهٔ جادویی UDP
        ▼
کارت شبکهٔ کامپیوتر خواب‌رفته
```

**بستهٔ جادویی** طبق استاندارد: ۶ بایت `0xFF` و بعد آدرس MAC مقصد ۱۶ بار تکرار شده —
مجموعاً ۱۰۲ بایت، از طریق UDP به پورت ۹.

بسته به **سه مقصد** فرستاده می‌شود، چون در عمل هر روتر یکی از این‌ها را می‌بندد:

1. آدرس IP خود دستگاه (اگر وارد شده باشد) — وقتی جدول ARP روتر هنوز گرم است کار می‌کند
2. `255.255.255.255` — broadcast محدود
3. broadcast مستقیم هر اینترفیس، که از IP و netmask خود تلویزیون محاسبه می‌شود

هر مقصد چند بار (پیش‌فرض ۳ بار) ارسال می‌شود، چون اولین بستهٔ UDP اغلب گم می‌شود.

**پل ارتباطی** روی `PalmServiceBridge` ساخته شده، نه `webOSTV.js`؛ این تابع را خود
پلتفرم در همهٔ نسل‌های webOS TV فراهم می‌کند، پس فایل شخص ثالثی برای به‌روز نگه‌داشتن
لازم نیست.

## ⚠️ محدودیت مهم سرویس Node — این را بخوان قبل از دست زدن به `service/service.js`

سرویس روی **Node بسیار قدیمی** اجرا می‌شود. نقشهٔ نسخه‌ها:

| نسخهٔ webOS TV | نسخهٔ Node |
|---|---|
| 3.x و 4.x | **v0.12.2** |
| 5.0 و 6.0 | v8.12.0 |
| 22 و 23 | v12.x |
| 25 و 26 | v16 / v20 |

Node 0.12 **Promise ندارد** (از Node 4 اضافه شد) و طبق مستندات خود ال‌جی، webOS 4.x و
پایین‌تر **هیچ نحو ES6 را پشتیبانی نمی‌کنند**: بدون `const`، `let`، arrow function،
destructuring و template literal.

پس `service/service.js` باید `var`، `function` و callback بماند. یک `Promise` تنها
کافی است تا سرویس در لحظهٔ بارگذاری خطا بدهد و سقوط کند — و روی تلویزیون این دقیقاً
شبیه «سرویس وجود ندارد» دیده می‌شود، بدون هیچ پروسه‌ای که بشود بررسی کرد.

این محدودیت به `js/*.js` مربوط نیست: آنها در کرومیوم اجرا می‌شوند و Promise در
آنها بی‌اشکال است.

`npm test` دو آزمون نگهبان دارد که اگر کسی سرویس را «مدرن» کند فوراً می‌شکند:
نبود نحو ES6، و نبود `return` در سطح بالای ماژول (که minify را می‌شکند).

### ساختار پوشهٔ سرویس هم مهم است

سرویس یک پکیج مستقل است و `services.json` باید **داخل پوشهٔ خودش** باشد، نه در ریشهٔ
اپ:

```
lg-wol/
├─ appinfo.json          اپ
├─ index.html
└─ service/              سرویس — این پوشه services.json دارد، پس ares-package
   ├─ package.json       آن را به‌عنوان سرویس می‌شناسد
   ├─ services.json
   └─ service.js
```

اگر `services.json` در ریشهٔ اپ بگذاری، `appinfo.json` بر آن اولویت می‌گیرد، پوشه
فقط «اپ» شناخته می‌شود، و سرویس هرگز روی luna ثبت نمی‌شود — نتیجه: اپ نصب و اجرا
می‌شود ولی هر کلیک خطای «service not exist» می‌دهد. برای تشخیص، بستهٔ ساخته‌شده باید
`usr/palm/services/<نام سرویس>/` داشته باشد.

### نام متدها با فریم‌ورک تداخل نکند

`webos-service` خودش متدهای توکاری مثل `/info` و `/quit` ثبت می‌کند و در تداخل
برنده می‌شود. مثلاً اگر متدی به نام `info` بسازی، اپ به‌جای پاسخ تو **فهرست متدهای
سرویس** را از فریم‌ورک می‌گیرد و آن بخش رابط بی‌سروصدا خراب می‌شود. به همین دلیل
متد این اپ `network` نام دارد، نه `info`.

## استفاده

### تب «دستگاه‌ها»

- **افزودن دستگاه**: نام، آدرس MAC (الزامی)، IP (اختیاری)، پورت و یادداشت.
- برای وارد کردن MAC روی تلویزیون، دکمهٔ **صفحه‌کلید** یک کیبورد شانزده‌شانزدهی
  باز می‌کند — تایپ کردن با کنترل تلویزیون عملاً غیرقابل استفاده است.
- **بررسی وضعیت**: یک «ping مبتنی بر TCP» می‌فرستد. اگر دستگاه به پورت بسته پاسخ
  RST بدهد، یعنی روشن است — بسته بودن پورت دلیل خاموش بودن نیست.
- **بیدار کن**: بسته را می‌فرستد. اگر «بررسی خودکار» روشن باشد، ۶، ۱۴ و ۲۶ ثانیه
  بعد دوباره وضعیت را می‌پرسد (بوت شدن زمان می‌برد) و به‌محض پاسخ، متوقف می‌شود.

### تب «کشف شبکه»

- **شبکهٔ این تلویزیون**: آدرس‌ها و broadcast محاسبه‌شده.
- **جست‌وجوی شبکه**: کل `/24` محلی را روی پورت‌های ۹، ۸۰ و ۴۴۳ می‌کاود.
  فقط دستگاه‌های **بیدار** پاسخ می‌دهند.
- **جدول ARP**: مهم‌ترین بخش این تب. جدول ARP هسته اغلب MAC دستگاه‌هایی را نگه
  می‌دارد که **همین حالا خوابیده‌اند** — یعنی همان چیزی که برای بیدار کردنشان لازم
  دارید و جای دیگری پیدا نمی‌شود. روی هر ردیف بزنید تا مستقیم به فهرست دستگاه‌ها
  اضافه شود.

### تب «تنظیمات»

زبان (فارسی/انگلیسی/کره‌ای)، پورت پیش‌فرض، تعداد بسته‌ها، فاصله و مهلت زمانی،
آدرس broadcast اضافی، عیب‌یابی، و پشتیبان‌گیری (نوشتن فهرست دستگاه‌ها در یک فایل
روی تلویزیون و بازگردانی آن روی تلویزیون دیگر).

## آماده کردن دستگاه مقصد

بدون این تنظیمات، هیچ اپی نمی‌تواند کامپیوتر شما را بیدار کند.

### ویندوز

1. **بایوس/UEFI**: گزینهٔ `Wake on LAN`، `Power On By PCI-E` یا `Resume by LAN` را فعال کنید.
2. **کارت شبکه**: Device Manager → کارت شبکه → Properties →
   - تب **Power Management**: «Allow this device to wake the computer» و
     «Only allow a magic packet to wake the computer» را تیک بزنید.
   - تب **Advanced**: `Wake on Magic Packet` = Enabled.
3. **Fast Startup را خاموش کنید** (Control Panel → Power Options →
   Choose what the power buttons do → Turn on fast startup را بردارید).
   با روشن بودن Fast Startup، «Shutdown» در واقع hibernate است و بیدار کردن
   از آن حالت معمولاً کار نمی‌کند.
4. بیدار شدن از حالت **Sleep** تقریباً همیشه کار می‌کند. از حالت **Shutdown (S5)** فقط
   اگر مادربورد و کارت شبکه در حالت آماده‌به‌کار برق داشته باشند.

### لینوکس

```bash
sudo ethtool eth0 | grep Wake-on        # باید "Wake-on: g" را نشان دهد
sudo ethtool -s eth0 wol g              # فعال کردن موقت
```

برای دائمی کردن، یک واحد systemd بسازید یا از NetworkManager استفاده کنید:

```bash
nmcli connection modify "Wired connection 1" 802-3-ethernet.wake-on-lan magic
```

### مک

مک‌های اینتل با Ethernet: System Settings → Energy → «Wake for network access».
مک‌های **Apple Silicon** از بیدار شدن با magic packet پشتیبانی نمی‌کنند و این اپ
روی آن‌ها کار نمی‌کند. AirPort/Thunderbolt-Ethernet هم در خواب پیوند شبکه را از دست
می‌دهد.

### شبکه

- تلویزیون و مقصد باید روی **یک سگمنت L2** باشند (همان سوئیچ/VLAN). broadcast از
  روتر عبور نمی‌کند مگر با `ip helper-address` پیکربندی شده باشد.
- **Wi-Fi**: اگر مقصد با وای‌فای وصل است، بیدار کردن تقریباً هیچ‌وقت کار نمی‌کند، چون
  کارت وای‌فای در خواب اتصال را رها می‌کند. برای مقصد، کابل شبکه لازم است.
- بیدار کردن از بیرون خانه نیاز به فوروارد کردن پورت ۹/UDP در روتر دارد + entry
  ثابت ARP. این اپ فقط داخل شبکهٔ خانه کار می‌کند.

## عیب‌یابی

**اول از همه: تنظیمات → عیب‌یابی → «اجرای آزمون».**
این آزمون یک بستهٔ واقعی می‌فرستد و می‌گوید نرم‌افزار همین تلویزیون چه چیزی را
اجازه می‌دهد:

- `udp.ok: false` → سخت‌افزار webOS اجازهٔ broadcast نمی‌دهد. با `npm run log`
  کد خطا را دقیق ببینید.
- `arp.ok: false` → `/proc/net/arp` روی این نرم‌افزار قابل خواندن نیست؛ MAC را دستی
  وارد کنید. بقیهٔ اپ کار می‌کند.

| نشانه | علت احتمالی |
|---|---|
| «بسته ارسال شد» ولی دستگاه روشن نمی‌شود | تنظیمات WOL خود دستگاه مقصد (بالا) یا نبودن در یک سگمنت |
| هیچ پاسخی از سرویس نمی‌آید | سرویس بالا نیامده — `npm run log` را ببینید |
| «بررسی وضعیت» همیشه خاموش نشان می‌دهد | IP وارد نشده، یا فایروال مقصد probe را می‌اندازد دور. بسته بودن پورت طبیعی است؛ نبودن پاسخ نیست |
| روتر `255.255.255.255` را مسدود می‌کند | در تنظیمات، «آدرس broadcast اضافی» را روی مثلاً `192.168.1.255` بگذارید |
| از خواب بیدار می‌شود ولی از Shutdown نه | Fast Startup ویندوز یا نبودن برق روی کارت شبکه در S5 |

برای اینکه مطمئن شوید **مقصد** اصلاً با WOL بیدار می‌شود، از یک کامپیوتر دیگر
تست کنید؛ این اپ را از معادله بیرون می‌کند:

```bash
wakeonlan AA:BB:CC:DD:EE:FF          # لینوکس/مک
# یا
etherwake -i eth0 AA:BB:CC:DD:EE:FF
```


### چند تصمیم طراحی که ممکن است سؤال‌برانگیز به نظر برسند

- **بدون فریم‌ورک.** کل اپ پنج نماست؛ هزینهٔ یک build step و runtime از خود این
  فایل بیشتر می‌شد.
- **بدون CSS Grid و بدون `async/await`.** کرومیوم تلویزیون‌های قدیمی‌تر این‌ها را
  ندارد. فقط flexbox و Promise.
- **جدول سازندهٔ MAC آفلاین است.** هیچ درخواست شبکه‌ای در اپ وجود ندارد؛ هم برای
  بازبینی فروشگاه بهتر است، هم وعدهٔ «هیچ داده‌ای از خانه بیرون نمی‌رود» را واقعی
  نگه می‌دارد.
- **فوکوس با کلاس CSS جابه‌جا می‌شود، نه با `element.focus()`.** اگر فوکوس واقعی
  روی کادر متنی برود، کیبورد روی صفحه بالا می‌آید؛ این فقط وقتی اتفاق می‌افتد که
  کاربر با Enter روی کادر متنی تأیید کند.

## وضعیت آزمون

**نصب‌شده و آزموده‌شده روی یک تلویزیون واقعی** (LG 43LK6100PVA، webOS 4.4، Node
v0.12.2). نتیجهٔ آزمون عیب‌یابی روی خود دستگاه:

```
udp.ok: true
  → 255.255.255.255:9  ارسال موفق
  → 192.168.2.255:9    ارسال موفق
  → 192.168.1.255:9    ارسال موفق
arp.ok: true, count: 2      (جدول ARP روی این تلویزیون خوانده می‌شود)
interfaces: eth0 192.168.2.90/24 و wlan0 192.168.1.176/24
```

و یک بیدارباش واقعی از داخل خود اپ:

```
delivered = 12/12
targets   = 192.168.2.91, 255.255.255.255, 192.168.2.255, 192.168.1.255
```

یعنی **سخت‌افزار این نسل از تلویزیون اجازهٔ broadcast می‌دهد و WOL از آن کار
می‌کند.** رابط کاربری هم روی دستگاه آزموده شد: تب‌ها، مودال افزودن دستگاه، صفحهٔ
کلید MAC، فوکوس خودکار و تب کشف شبکه همه درست کار می‌کنند.

آزمون‌های خودکار:

- **۲۸ بررسی با `npm test`** — منطق بستهٔ جادویی (۱۰۲ بایت، شش بایت `0xFF`، شانزده
  تکرار MAC، تطابق کامل هگز)، نرمال‌سازی MAC، محاسبهٔ broadcast برای `/8`، `/16`،
  `/24` و `/25`، تجزیهٔ `ip neigh` و `arp -a`، کاوش TCP، و دو آزمون نگهبان سازگاری
